# HU-016 — Gatear la administración de roles: solo quien administra la aplicación define roles y concede recursos

> Origen: primera historia del backlog de cierre de HU-009 (ver `ADR-023-application-administration-model.md`

> Prioridad #1 del backlog siguiente a HU-015, decidida explícitamente por Sebastián: cerrar la brecha
> de mínimo privilegio antes que el autoservicio de administradores (HU-020).
>
> **Depende de HU-009** (ya entregada — `PrincipalMustBeApplicationAdministratorValidator`, publicado
> como `authorization :: rule`) **y de HU-015** (patrón de cableado ya probado en `applications`) **y

## Por qué existe esta historia

Hoy, `DefineRoleUseCase` (crear un rol) y `GrantResourceToRoleUseCase` (conceder un recurso a un rol)
siguen abiertos a **cualquier usuario autenticado del tenant** — el mecanismo de HU-009 existe desde
hace una historia y solo protege `RemoveApplication`/`RotateApplicationCredential` (HU-015). Cualquier
miembro de un tenant puede hoy crear un rol de alcance `APPLICATION` para una aplicación que no
administra, o concederle un recurso protegido de esa aplicación a un rol arbitrario. Es la brecha de
mínimo privilegio (INV-SEC-04) más directa que queda abierta en el catálogo.

## Enunciado

> Como **administrador de una aplicación**, quiero **que solo yo (o quien también la administra)
> pueda definir sus roles y concederles recursos**, para que la seguridad de mi aplicación no dependa
> de que ningún otro miembro del tenant decida tocarla.

## Lo que hay que decidir antes de planificarla

1. **`GrantResourceToRoleUseCase` recibe un rol y un recurso, potencialmente de aplicaciones
   distintas si algo estuviera mal formado — ¿de cuál `applicationId` se exige administración?**
   Candidato obvio: del rol (es el que gana el recurso), pero el planificador debe confirmar que el
   modelo no permite hoy un rol y un recurso de aplicaciones distintas (si `RegisterProtectedResourceUseCase`
   ya lo impide en otra capa, esta historia no necesita repetir la validación, solo gatear con el
   `applicationId` correcto).
2. **¿Qué pasa con roles y concesiones que ya existen, creados antes de esta historia por un usuario
   que no era ni es administrador?** Ninguna migración de datos parece necesaria (la regla es sobre
   quién puede *escribir* de aquí en adelante, no sobre lo ya escrito) — pero el planificador debe
   decirlo explícitamente en el plan, no dejarlo implícito.
3. **Mensaje de error**: ¿reutiliza `NotAuthorizedToAdministerException` tal cual (mismo código HTTP y
   cuerpo que HU-015 ya usa para `applications`), o necesita un `reasonCode`/mensaje que distinga "no
   administras esta aplicación" al crear un rol de "no administras esta aplicación" al conceder un
   recurso? Precedente de HU-015: un solo tipo de excepción para las dos operaciones que gateó.

## Alcance

**Cubre:** gatear `DefineRoleUseCase` y `GrantResourceToRoleUseCase` (slice `roles`) para roles de
alcance `APPLICATION` únicamente.

**No cubre:** roles de alcance `TENANT`/`GLOBAL` (ver tabla arriba); `resources` (HU-017);
`assignments` (HU-018); `profiles` (HU-019); autoservicio de administradores (HU-020); auditoría de
esta operación como evento propio (HU-021, cubre todas las historias de este backlog de una vez).

## Criterios de aceptación (alto nivel — el plan los detalla)

1. Un administrador de la aplicación puede definir un rol de alcance `APPLICATION` para ella y
   conceder recursos a ese rol.
2. Un usuario autenticado del tenant que **no** administra esa aplicación recibe rechazo
   (`NotAuthorizedToAdministerException` o equivalente) al intentar cualquiera de las dos operaciones.
3. Un rol de alcance `TENANT`/`GLOBAL` sigue sin gatearse — cero regresión sobre el comportamiento
   actual para esos alcances.
4. `verificar.ps1` (suite completa) sigue en verde; `ModulithStructureTests`/`LayeredArchitectureTests`
   sin cambios de frontera no justificados.
