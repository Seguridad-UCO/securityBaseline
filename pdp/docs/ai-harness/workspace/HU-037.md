# HU-037 — Canal bearer del microfrontend de seguridad (`getAccessToken` y `onError`)

> ✅ **Cerrada el 2026-10-30** (repositorio `security-ui`, commit `feat(auth): canal bearer con getAccessToken…`). Nueva. Surge de
> escribir la guía de integración para aplicaciones consumidoras: ADR-031 (Accepted) obliga a que el host entregue
> `getAccessToken()` y a que el componente lo envíe como `Authorization: Bearer`, y HU-025 (PoC) lo declaraba, pero el código de
> `security-ui` solo implementaba la cookie BFF (`credentials: "include"` + `X-XSRF-TOKEN`).
> **Depende de:** HU-026 (canal bearer en el PDP, ya cerrada), ADR-031, ADR-033 (el host renueva), ADR-027 (MFA).

## Por qué existe esta historia

Una aplicación externa con su propio login OIDC no podía usar el componente: la cookie BFF es de otro sitio y `SameSite=Lax` la
bloquea (ADR-031, alternativas descartadas). Sin canal bearer el microfrontend solo servía para el panel propio del PDP, que no es
el caso de integración que justifica el componente.

## Enunciado

> Como **equipo de una aplicación protegida**, quiero **montar el microfrontend de seguridad entregándole una función que devuelve
> mi token y recibir avisos cuando necesito reautenticar al usuario**, para integrarlo sin un segundo login ni compartir cookies.

## Decisiones

| Pregunta | Decisión |
|---|---|
| ¿Quién es dueño del token? | El host. `getAccessToken()` se invoca **antes de cada petición**; el componente no lo cachea ni lo guarda. |
| ¿Qué pasa con cookie y CSRF? | Con bearer no viaja ninguna cookie (`credentials: "omit"`) ni `X-XSRF-TOKEN`. Sin `getAccessToken` rige la cookie BFF, solo para el panel propio. |
| ¿Si el host no puede dar token? | No se llama al PDP: `ApiError` 401 `UNAUTHENTICATED` y aviso `unauthenticated`. |
| ¿Cómo se entera el host? | `onError({cause, status, code})` con `unauthenticated` (401), `mfa_required` (403 `MFA_REQUIRED`), `forbidden` (403) y `unavailable` (429/503). El componente **nunca reintenta**; un fallo del callback no tapa el error. |
| ¿El 403 muestra el cuerpo del PDP? | No: el texto sale del código (`MFA_REQUIRED`, `NOT_AUTHORIZED_TO_ADMINISTER_TENANT_CATALOG`). |

## Criterios y evidencia

| # | Criterio | Resultado |
|---|---|---|
| 1 | Con `getAccessToken`, cada petición lleva `Authorization: Bearer` de una invocación nueva y no lleva cookie ni CSRF | ✅ `security-api.test.ts` |
| 2 | Sin `getAccessToken` se conserva la cookie BFF | ✅ |
| 3 | 401 ⇒ `unauthenticated` y una sola petición (sin reintento) | ✅ |
| 4 | Token no disponible ⇒ no se llama al PDP | ✅ |
| 5 | `MFA_REQUIRED`, `forbidden`, 429 y 503 clasificados para el host | ✅ |

## Límites

- No se probó contra un navegador real ni contra un host con Keycloak propio; el canal bearer del PDP (HU-026) está cubierto por sus
  propias pruebas y por los flujos Hurl del edge. La prueba de punta a punta con un host de ejemplo queda como siguiente paso del
  equipo que integre.
- El `dist/` estaba desfasado respecto de `src/` desde ADR-033; se regeneró aquí.
