# HU-038 — El canal Bearer aprovisiona la identidad local del usuario

> Nueva (2026-10-30). La encontró la prueba E2E del canal Bearer (`e2e/`, hallazgo 2). **Depende de:** HU-026.
> Es el criterio 5 de HU-026 («un usuario válido que nunca entró al panel propio queda aprovisionado al primer uso») que no está cumplido.

## Por qué existe

`ProvisionIdentityUseCase` solo se invoca desde `OidcAuthenticationSuccessHandler` (login por el panel). `RevocationAwareJwtDecoder` necesita la
identidad local (`SubjectUserIdLookupValidator`) para comprobar la revocación por usuario; si no existe, el token se rechaza con
`401 UNAUTHORIZED`. Resultado: una aplicación host con su propio login no puede usar a ningún usuario que no haya ingresado antes por el panel.

## Enunciado

> Como **aplicación host**, quiero **que un usuario con token válido del realm quede reconocido por el PDP en su primera llamada**, para no
> obligarlo a entrar antes al panel de Seguridad.

## Decisiones propuestas (a validar en Gate 1)

- Aprovisionar en el camino Bearer con los claims mínimos (`sub`, `tenant`, `email`, `name`), de forma idempotente y **antes** de la comprobación de revocación.
- Fail-closed: si faltan claims o el aprovisionamiento falla, `401`; nunca un usuario creado a medias.
- El tenant sale del claim (no del tenant por defecto del BFF). Un tenant inactivo o inexistente rechaza.
- Concurrencia: dos primeras llamadas simultáneas no deben crear dos usuarios.

## Criterios (alto nivel)

1. Un token válido de un usuario nunca visto produce `200` y deja la identidad creada, sin pasar por el panel.
2. Token sin `tenant`, o de tenant inexistente/suspendido: `401`/`403` sin crear nada.
3. Dos llamadas simultáneas crean una sola identidad.
4. La revocación (ADR-026, ADR-034) sigue funcionando para el usuario recién aprovisionado.
5. `e2e/` sin el paso `first-login`.
