# HU-030 — Renovación del token de la sesión BFF para el canal PEP

> ✅ **Cerrada el 2026-10-28** (ver [REPORTE-HU-030](reportes/REPORTE-HU-030.md); queda el Hurl de Edge con HU-027). Nueva (2026-10-28). Surge de replantear HU-029: al verificar el código apareció el problema que ese
> endpoint nunca resolvió. Decisión en
> [ADR-033 §2](../../../../../security-platform-architecture/docs/01-governance/adr/ADR-033-token-renewal-ownership.md).
>
> **Depende de:** HU-029 (retira el proxy que comparte el almacén de refresh).
> **Toca:** `InternalBffSessionTokenController`, `OidcAuthenticationSuccessHandler`, `KeycloakSecurityConfiguration`.

## Por qué existe esta historia

El PEP resuelve la cookie BFF de un usuario pidiendo al PDP `GET /internal/v1/bff-session-token`
(`BffSessionTokenResolver` → `InternalBffSessionTokenController`). El controlador carga el
`OAuth2AuthorizedClient` de la sesión y devuelve `client.getAccessToken().getTokenValue()` **sin mirar si
expiró**. Nada en el código renueva ese access token. Consecuencia: cuando pasa la vida del access token
(minutos) y la sesión web sigue viva, el PEP reenvía a la aplicación un token vencido y todo el tráfico de ese
usuario falla hasta que vuelva a iniciar sesión.

El refresh token útil ya está dentro del mismo `OAuth2AuthorizedClient` (Spring Security lo guarda al hacer el
login). Además, `OidcAuthenticationSuccessHandler` guarda una **segunda copia** en Redis
(`RedisRefreshTokenStoreAdapter`, clave `oidc-refresh-token:{sid}`) cuyo único lector era el proxy de HU-029.
Esa copia añade una dependencia frágil: el login falla (`KeycloakAuthorizationCodeTokenResponseClient` /
`KeycloakRefreshTokenExpirationTracker`) si Keycloak no devuelve `refresh_expires_in`.

## Enunciado

> Como **aplicación detrás del PEP con una sesión de panel viva**, quiero **que el token que el PEP me
> reenvía esté siempre vigente mientras la sesión no haya expirado**, para que mi tráfico no falle cada vez
> que vence el access token.

## Lo que ya está decidido (no reabrir)

| Pregunta | Decisión | De dónde sale |
|---|---|---|
| ¿Dónde se renueva? | En el PDP, del lado servidor, dentro de `InternalBffSessionTokenController`. Sin endpoint público nuevo | ADR-033 §2 |
| ¿Con qué refresh token? | El del cliente BFF guardado en el `OAuth2AuthorizedClient` de la `WebSession` | ADR-033 §2 |
| ¿Mecanismo? | `ReactiveOAuth2AuthorizedClientManager` con proveedor `refresh_token`; persiste la rotación en la sesión | ADR-033 §2 |
| ¿Qué pasa con el almacén Redis de refresh y el tracker? | Se retiran: `RefreshTokenStorePort`, `RedisRefreshTokenStoreAdapter`, `KeycloakRefreshTokenExpirationTracker`, `KeycloakAuthorizationCodeTokenResponseClient` y su cableado | ADR-033 §2 |
| ¿Concurrencia? | Single-flight por sesión: dos peticiones simultáneas no canjean el mismo refresh token dos veces | ADR-033 §2 |
| ¿Fail-closed? | Si la renovación falla (`invalid_grant` o Keycloak no disponible) no se entrega un token vencido: `401` si la sesión murió, `503` si Keycloak no responde | ADR-025 |
| ¿El navegador ve algún token? | No | ADR-022 |

## Lo que hay que decidir antes de planificarla

1. **Cuánto antes de expirar se renueva** (margen). Spring usa un `clockSkew` por defecto de 60 s; el
   planificador fija el valor y dónde se configura (propiedad `pdp.security.session.token-renewal-skew`).
2. **Cómo se implementa el single-flight** sin bloquear: p. ej. un `Mono` cacheado por `sid` en un mapa
   concurrente con expulsión, o un atributo de la `WebSession`. Debe ser correcto con una sola instancia
   del PDP (el almacén de `WebSession` actual es en memoria; multi-instancia queda fuera de alcance y se
   declara).
3. **Qué hace el logout con el refresh token del cliente BFF.** Hoy `SessionRevocationController` y
   `KeycloakLogoutController` lo borran del almacén Redis; al retirar el almacén, el refresh token muere
   con la `WebSession` invalidada. El planificador confirma que no queda un refresh vivo en Keycloak más allá
   del RP-initiated logout.
4. **Qué ve el login si Keycloak no devuelve refresh token.** Hoy falla. Debe seguir siendo explícito, pero
   sin el requisito de `refresh_expires_in`.

## Alcance

**Cubre:**
- Renovar el access token de la sesión BFF antes de entregarlo al PEP, con single-flight y fail-closed.
- Retirar el almacén Redis de refresh y todo su cableado, y simplificar `OidcAuthenticationSuccessHandler`.
- Pruebas de integración con un Keycloak simulado: token vigente (no renueva), vencido (renueva y
  persiste la rotación), `invalid_grant` (401), Keycloak caído (503), concurrencia (un solo canje).
- Hurl de Edge que demuestre que, pasada la vida del access token, el PEP sigue recibiendo uno vigente.

**No cubre:**
- Sesiones distribuidas (Spring Session sobre Redis) — decisión aparte si se despliegan varias instancias.
- Renovación de tokens de aplicaciones externas (ADR-033: cada cliente la suya).
- Cambios en Keycloak (vida del access token, rotación de refresh tokens).

## Criterios de aceptación (alto nivel — el plan los detalla)

1. Con un access token vencido y sesión viva, `GET /internal/v1/bff-session-token` devuelve un token
   distinto y vigente, y la sesión guarda el refresh token rotado.
2. Con el access token vigente no se llama a Keycloak.
3. Dos peticiones concurrentes sobre una sesión con token vencido producen **un** canje contra Keycloak.
4. Si Keycloak responde `invalid_grant`, la respuesta es `401` y no se entrega ningún token.
5. Si Keycloak no responde, la respuesta es `503`; nunca se entrega un token vencido.
6. No quedan `RefreshTokenStorePort`, `RedisRefreshTokenStoreAdapter`, el tracker ni el wrapper de
   `refresh_expires_in`; el login funciona aunque Keycloak no envíe `refresh_expires_in`.
7. El navegador nunca recibe un token (respuesta de `/api/v1/session` y del callback sin tokens).
8. `verificar.ps1` (suite completa, con cobertura) en verde; `drift.ps1` y `consistencia.ps1` limpios.
