# HU-004 — Catálogo de roles: alcance y recursos que autoriza

> Origen: BC-04 (Roles) en `security-platform-architecture`, `docs/02-domain/03-bounded-contexts.md`
> — «catálogo RBAC de roles y su vínculo a recursos/acciones». Invariante `INV-DAT-01`.
>
> **Depende de HU-002** (el `ResourceId` y el catálogo de recursos protegidos ya existen).
>
> **Historia partida el 2026-09-11.** El borrador original cubría roles **y** asignaciones en una
> sola historia; con las decisiones de abajo (tres niveles de alcance, y el rol persiste qué
> recursos autoriza) son dos slices completos, cada uno del tamaño de HU-003. Las asignaciones son
> ahora **HU-005**. Ver `ROADMAP-PDP.md`.

## Por qué existe esta historia

Hoy el PDP sabe qué tenants, aplicaciones y recursos existen, pero no tiene vocabulario para decir
«este conjunto de recursos se concede junto». Esta historia produce ese vocabulario: el **rol** como
entrada del catálogo, con su alcance y los recursos que autoriza.

Es el primer paso de «el valor propio del PDP»: sin roles no hay asignaciones (HU-005), y sin
asignaciones OPA no tiene atributos que evaluar (HU-006).

## Enunciado

> Como **administrador de un inquilino**, quiero **definir roles con alcance y decir qué recursos
> protegidos autoriza cada uno**, para que las políticas evalúen sobre un catálogo declarado y no
> sobre reglas escondidas en código.

## Decisiones tomadas (respuestas de Sebastián, 2026-09-11)

| Pregunta | Decisión | Consecuencia |
|---|---|---|
| Alcance del rol | **Los tres niveles**: tenant, aplicación, global (`INV-DAT-01`) | `RoleScope` como value object con el nivel y, según el nivel, el `TenantId` o el `ApplicationId` |
| ¿El rol lleva vínculo a recurso/acción? | **Sí** — persiste qué `ResourceId` autoriza | Es **dato de catálogo que viaja a OPA como evidencia**, no una rama en Java: ningún caso de uso del PDP decide nada leyendo esa lista. La regla del roadmap («ni un solo `if (rol == ...)`») sigue intacta |
| ¿Quién administra el catálogo? | Se difiere a **HU-009** | Hasta entonces, el endpoint solo permite crear roles de **tenant** o de **aplicación** dentro del tenant del principal. Los roles **globales** existen en el modelo y en la persistencia, pero **no se pueden crear por HTTP** en esta historia — sin control de administración, cualquier usuario autenticado podría crear uno visible para todos los inquilinos |

## Criterios de aceptación

| # | Criterio | Resultado esperado |
|---|---|---|
| 1 | Alta de rol de tenant | Un rol con alcance de tenant queda registrado para el tenant del principal |
| 2 | Alta de rol de aplicación | Un rol con alcance de aplicación queda registrado; la aplicación debe existir y pertenecer al tenant del principal |
| 3 | Nombre único dentro del alcance | Dos roles con el mismo nombre en el mismo alcance → 409; el mismo nombre en dos tenants distintos → permitido |
| 4 | Recursos coherentes con el alcance | Conceder a un rol un recurso de una aplicación de **otro** tenant, o de otra aplicación cuando el rol es de aplicación → rechazado (`INV-DAT-01`) |
| 5 | Recurso inexistente | Conceder un `ResourceId` que no está en el catálogo → rechazado, con la excepción que ya publica `resources` |
| 6 | Consulta por tenant | El catálogo devuelve los roles del tenant del principal **más** los globales; nunca los de otro tenant |
| 7 | Global no creable aún | Intentar crear un rol global por HTTP → 400 con mensaje claro (no 500, no silencioso) |

## Alcance

**Entra:**
- Slice `pdp/roles` con las tres capas completas.
- `Role` (agregado), `RoleName`, `RoleScope` (nivel + tenant/aplicación según el nivel) como value objects; `RoleId` en `pdp/commons` porque HU-005 lo consumirá.
- Reglas puras: nombre único por alcance; alcance coherente con el recurso concedido; el recurso debe existir (validador prestado de `resources`); la aplicación debe existir y ser del tenant (validador prestado de `applications`).
- Casos de uso: crear rol, conceder recurso a rol, listar roles del tenant (+ globales).
- Endpoints `POST /api/v1/roles`, `POST /api/v1/roles/{roleId}/resources`, `GET /api/v1/roles`.
- Persistencia en SurrealDB: tabla `role` con índice único `(scope, tenantId, applicationId, name)`.

**No entra:**
- Asignar roles a usuarios — es **HU-005**.
- Perfiles como agrupación de roles — es **HU-008**.
- Restringir quién puede administrar el catálogo — es **HU-009**. Consecuencia: los roles globales no se crean por HTTP en esta historia.
- Herencia de roles y denegaciones explícitas (`RB-14`): el propio repositorio de arquitectura la marca **«pendiente»**; no se planifica lo que el dominio no ha decidido.
- Enviar nada a OPA — es **HU-006**.
- Cualquier `if (rol == ...)` o `if (recurso in rol.recursos)` en un caso de uso: el catálogo es dato de entrada para la política, jamás una decisión en Java.

## Riesgo a vigilar

Con el vínculo rol→recurso persistido, la tentación es «ya que sabemos qué recursos autoriza el rol,
decidamos aquí». No: el PDP responde **qué recursos declara autorizar** un rol; **si eso concede el
acceso** lo decide OPA con la política. La única lógica de este slice es de integridad del catálogo.
