# HU-013 — El PDP valida la credencial de una aplicación

> Origen: `MAPA-PLATAFORMA-SEGURIDAD.md`, sección C (Librería), ítem "Evitar implementación manual"
> (🟡: *"Cubre el alta. El enforcement lo hace el PEP como proxy, no la librería"*) y hallazgo 1
> (*"dos registros de aplicaciones, y no se hablan"*). Compañera directa de **HU-012**: emitir una
> credencial sin forma de validarla no cierra la brecha — solo la traslada.
>
> **Depende de HU-012** (necesita que exista una credencial que validar).
>
> Borrador escrito el 2026-09-13 a pedido de Sebastián, en la misma tanda que HU-012.

## Por qué existe esta historia

Con HU-012 el PDP emite una credencial, pero si nadie la valida no reemplaza nada: el PEP seguiría
usando su propio `integrations.json` con un token repartido a mano, y los dos registros de
aplicaciones seguirían sin hablarse. Esta historia es la que efectivamente une los dos registros: le
da al PEP (o a quien necesite confiar en una aplicación) una forma de preguntarle al PDP "¿esta
credencial es válida para esta aplicación?", igual que ya existe `/internal/v1/access-decisions`
para las decisiones de autorización (HU-003).

## Enunciado

> Como **PEP**, quiero **poder validar contra el PDP la credencial que una aplicación presenta**,
> para no tener que mantener mi propio almacén de credenciales de aplicación desconectado del
> catálogo real.

## Lo que hay que decidir antes de planificarla

| Pregunta                                                         | Opciones sobre la mesa                                                                                                                                                                                                                         |
|------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| ¿Cómo se llama el consumidor a este endpoint?                    | Mismo canal interno que ya usa HU-003 (mTLS, `client-auth=want`) — no exponerlo por el canal BFF                                                                                                                                               |
| ¿Qué recibe el endpoint?                                         | El secreto en texto plano (el PDP lo compara contra el hash guardado) — nunca pedirle al llamante que compare hashes por su cuenta                                                                                                             |
| ¿Qué devuelve?                                                   | Válido/inválido, más los datos mínimos que el PEP necesite del catálogo (p. ej. `tenantId`, si la aplicación sigue activa) — sin filtrar el hash ni metadatos innecesarios                                                                     |
| ¿Reemplaza el flujo actual del PEP, o convive con él?            | El PEP hoy tiene su propio `integrations.json` con credenciales manuales; decidir si esta historia dejar ambos caminos activos (transición) o si migrar el PEP a consultar siempre al PDP queda para una historia del lado del PEP             |
| ¿Qué pasa si la aplicación no existe o su credencial fue rotada? | Responder "inválida" sin distinguir la causa en el cuerpo de la respuesta (para no filtrar si el problema es "no existe" vs. "credencial vieja") — mismo principio de no revelar más de lo necesario que ya aplica a autenticación de usuarios |

## Criterios de aceptación (borrador)

| # | Criterio              | Resultado esperado                                                                                                                                                                                                                             |
|---|-----------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 1 | Credencial válida     | El endpoint responde válida cuando el secreto coincide con el hash guardado para esa aplicación                                                                                                                                                |
| 2 | Credencial inválida   | Responde inválida si el secreto no coincide, si la aplicación no existe, o si fue rotada (HU-014) — mismo mensaje para las tres, sin distinguir la causa                                                                                       |
| 3 | Canal interno, no BFF | El endpoint vive en el mismo controlador/canal interno que ya usa mTLS (HU-003), no en `/api/v1/`                                                                                                                                              |
| 4 | Sin fuga de datos     | La respuesta nunca incluye el hash del secreto ni el secreto mismo                                                                                                                                                                             |
| 5 | Auditable             | Cada validación (válida o no) es candidata a auditoría — decidir en el plan si reutiliza `AccessAuditRepository` (HU-007) o si es un evento propio, dado que no es una decisión de autorización de usuario sino de autenticación de aplicación |

## No entra

- **Migrar** el `pep/starter` o el PEP mismo para que dejen de usar `integrations.json` — eso es
  trabajo del lado del PEP, y puede ser una transición gradual fuera de esta historia.
- **Emitir** la credencial — es HU-012.
- **Rotar** la credencial — es HU-014.
